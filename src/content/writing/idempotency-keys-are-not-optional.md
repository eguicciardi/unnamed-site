The first time it happened we lost about four hours to it. A mobile client on a bad train connection fired the same charge request twice, six seconds apart, and both of them succeeded. The second request was not a bug in the client — it was the client doing exactly what a well-behaved HTTP client does when a response never arrives.

The fix is old and well understood: let the caller name the operation, and make the server promise that a name is only ever executed once. What is less understood, in my experience, is where that promise actually has to live.

## The key belongs to the intent, not the request

A tempting first implementation hashes the request body and calls that the key. It works until the same user legitimately wants to send the same body twice — two identical €12 top-ups, ten minutes apart, are not a duplicate. They are two top-ups.

The key has to be generated by the client at the moment the user expresses an intent — when the button is pressed, not when the request is serialised — and it has to be reused for every retry of that intent, including retries after an app restart.

```http
POST /v1/charges
Idempotency-Key: 5f2a9c7e-0d31-4a6b-9f10-c7b1e2d84a03
Content-Type: application/json

{ "amount": 1200, "currency": "EUR", "source": "card_9f2" }
```

## Store the response, not just the key

A key table that only records "this key was seen" solves double-charging and nothing else. The retrying client still has no answer, so it retries again, and now you are returning 409s to a client that simply wants to know what happened the first time.

Persist the full response — status code, body, and the id of the resource you created — keyed by the idempotency key and scoped to the authenticated account. On a repeat, replay it verbatim.

> A retry should be indistinguishable from the original call. If your client has to handle a special "already done" branch, the abstraction has leaked.

## The three states that actually matter

- **Unseen** — no row for this key: claim it and start the work in the same transaction.
- **In flight** — the row exists but has no stored response yet: return 409 with a Retry-After, never a fresh execution.
- **Settled** — a stored response exists: replay it byte for byte, with the original status code.

That middle state is the one everybody forgets. Two requests with the same key can be in flight simultaneously; if the second one reads the table before the first one writes its result, you are back to double-charging. Insert the key row inside the same transaction that starts the work, and let the unique constraint reject the second writer.

## Expiry is a product decision

Keys cannot live forever, but the expiry window is not an infrastructure concern. Twenty-four hours is the usual default and it is usually wrong: a client that retries a failed payment the next morning deserves the replay, not a fresh charge. Pick the window from how long the intent stays meaningful to the user, then size the table for it.

None of this is difficult. It is just easy to leave until the day you find two charges with the same amount, six seconds apart, and a customer who is entirely right to be annoyed.
